# 性能分析的读数与排查方法（v1.5.0）

旧版把物理步／帧放在「物理压力」图里，容易把掉帧后的补步误认为物理耗时上升。新版将调度、真实计时、对象状态与跟踪器自身开销分开；仍然零 Harmony 补丁，正常采样不写入游戏对象。

## 先看哪些读数

| 读数 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 平均／最长帧耗时、超过50ms的帧数 | 实际墙钟帧间隔；区分持续低帧与单次卡顿 | 单凭它不能定位物理、网络或渲染 |
| 2D模拟平均／峰值（导出含两项） | 引擎提供准确的 `Physics2D.Simulate` 纳秒计时源时，记录其耗时 | 来源不可用时显示「不可用」；不根据调度或CPU推算，也不填零；不代表全部物理相关脚本耗时 |
| 步／秒与设定步／秒 | FixedUpdate调度频率与 `timeScale / fixedDeltaTime` 的对照 | `FixedUpdate` 不是单个物体的物理计算次数 |
| 步／帧 | 相邻渲染帧间执行了几次 FixedUpdate | 不是毫秒、CPU负载或物理压力。50Hz配60fps约0.83；同样50Hz配约13.44fps可达3.72 |
| 注册物品／启用物品 | 原版 `Item.allItems` 中仍存活的对象，以及启用的部分 | 不含尚未注册的对象；数量不等于渲染数、物理副本数，也不直接证明复制 |
| 无父级动态物品：清醒／休眠 | 启用、无父级、启用模拟且Dynamic刚体的状态 | 无父级不等于无主；休眠物体也不能称为正在积极模拟的物体 |
| 向下运动 | 上述清醒物品中采样时竖直速度小于-2的数量 | 单次速度不证明持续下坠或穿图 |
| 无实体碰撞（可选） | 上述清醒物品未找到启用的、非Trigger、属于同一刚体的有效碰撞体 | 无碰撞本身不证明异常；触发器不算实体碰撞 |
| 场景刚体／清醒／休眠／碰撞体（可选） | 已加载场景和常驻场景中启用对象的物理组件状态；不局限于物品 | 不是引擎内部接触对数、碰撞测试次数或物理CPU负载 |
| 玩家数、网络条目数 | Together对应字典的条目数，反射缺失显示不可用／-1 | 不逐条判定死亡或断线，条目数不等于健康在线人数 |
| CPU／GC／托管堆 | 进程全核心平均CPU、采样间隔内各代GC次数、托管内存变化 | CPU低不排除单线程瓶颈，托管堆不是游戏总内存 |
| 自身平均／峰值耗时 | 跟踪器Update和页面代码在主线程花的CPU时间，按上一完整帧归集 | 不含GPU、引擎异步工作，也不是跟踪器对帧率影响的完整因果测量 |
| CPU主线程／渲染线程／GPU（可选） | 准确原生计时器返回的阶段时间，CPU与GPU分开看 | 存在数帧延迟，不能相加，不提供具体函数调用栈；GPU零值按无有效数据处理 |
| 呈现等待／主动限帧等待（可选） | 分辨呈现或主动等待目标帧率的时间 | 呈现等待本身不能区分GPU忙、同步或其他渲染等待；正常限帧等待属于状态提示 |

排查「一个客机退出，另一个客机掉帧」时，先在受影响客机打开性能分析，留一段基线，退出前后点「标记并清点」。比较帧耗时、准确2D计时（若可用）和清醒物品的变化；再按需开启详细场景统计与物品碰撞检查。主机也导出一份，结合MPfix清理日志。采样每秒一次，玩家数变化检测最多还会受此间隔影响；不能把自动标记当成精确断线时刻。

对象分帧清点，不保证同一时刻的原子快照。页面显示上次完整清点距今多久和清点跨度，日志保存起止时间；下一次清点未结束时继续显示旧结果。详细统计关闭后保留历史并注明关闭，避免伪造为零。启用的旧对象变成无父级／清醒，和真正新生成一批对象，需要结合注册数与状态数区分，不能只看刚体总数。

## 减少观察者开销

- 默认1秒保存一点，物品清点默认15秒一次；页面未打开过时不做对象清点或计时源探测。默认关闭额外的场景树遍历与碰撞检查。
- 复用物品引用数组与组件列表；每帧共享0.4ms清点预算（可调0.1～2ms），物品至多64件、场景至多128次操作；两者轮流优先。玩家数改变后10秒内临时每秒清点物品。
- 单次引擎调用和引用数组复制无法中途打断，预算不是绝对上限。慢分片记录真实开销并退避100ms；大场景下仍需观察自身峰值。
- 固定容量环形历史避免逐次移动整个列表。图表每次新数据／尺寸变化才生成缓存纹理，保留每个时间像素的最高和最低值；每帧每图一次贴图绘制。关掉窗口后继续记录，但不绘制图表。
- 暂停／关闭采样后停止计时器和清点，恢复时重置统计窗口，图表不跨暂停区间连线。日志只有点导出才写盘，采用缓冲写入；兼容旧WriteLog键，不恢复逐行实时写盘。

## CPU／GPU阶段计时与明显标记

「阶段计时」默认关闭，按需连接7个准确的纳秒计时器：`CPU Total Frame Time`、`CPU Main Thread Frame Time`、`CPU Render Thread Frame Time`、`GPU Frame Time`、`Gfx.WaitForPresentOnGfxThread`、`WaitForTargetFPS`、`PlayerLoop`。不替换PlayerLoop，不启用深度分析，不改游戏帧率。计时器可用不代表已经返回数据；前8次读取预热，缺失显示「不可用」，窗口失焦时不评估渲染/GPU，避免把保留值当作当前负载。

Unity支持按计时器收集阶段数据，并提示计时可能延迟数帧、采集自身有成本；不能用同一时刻显示的CPU/GPU读数还原精确调用顺序。参见 [Unity 2022.3 FrameTimingManager](https://docs.unity3d.com/2022.3/Documentation/Manual/frame-timing-manager.html)。正常采样不直接调用全量CaptureFrameTimings，只读启用的计时器；引擎内部采集成本未必出现在跟踪器自身CPU中。

- **红色＋文字**：FPS低于警戒（沿用默认45fps）、最长帧≥50ms。表示已观测到低帧/长帧，不等于确认性能故障，主动限帧也可能满足条件。
- **橙色＋文字**：CPU主线程/渲染线程/GPU平均开销≥参考帧预算的80%；可用2D模拟平均≥50%；自身峰值≥2ms与预算15%中的较大值。参考帧率默认60，可调，只用于诊断。
- **蓝色**：主动限帧等待、玩家/数量/GC等状态变化；物理步／帧变化明确解释为补步线索。低帧伴随呈现等待较大时使用橙色「原因未定」，不能直接判为GPU瓶颈。
- **灰色**：关闭、预热、失焦未评估或缺失。没有数据不表示已排除该瓶颈。

页面保留采样时间与数据年龄；四张缓存图表改为2×2，详细场景刚体以文字显示。「突变记录」可翻看最近160条事件，文字缓存并只绘制当前可见的行；默认页面显示最近两条说明。

## 突变规则与记录时间

帧间隔、自身CPU、可用阶段与物理计时逐帧观察，先积累12次有效读数，再与近期平滑基线比较。默认同时满足≥2倍且增量≥8ms才记录；自身CPU增量使用不高于2ms的阈值。物品、清醒/休眠刚体和网络条目同时满足倍数与默认50件绝对变化才记录，不会因1变2就报警。玩家数变化另行记录；托管堆大幅变化与完整GC只作为关联线索。世界/连接变化、恢复采样或改设置时重建基线，保留事件历史。

每个事件保留观测时间、前值、后值、触发规则、解释；默认3秒内同指标反复发生则合并，保留首次与末次时间、次数和峰值。低帧事件保存最低FPS。耗时事件使用读取时刻，对象事件使用完整清点结束时间，同时记录前次清点时间，因此不会把跨数秒的数量变化伪装成瞬时事件。GPU/原生阶段延迟在界面与日志注明，不反推虚构的精确发生时刻。

## 日志与验证

日志位于 `BepInEx/config/DDEN/perf-<UTC时间>.log`，`schema=3`；未知数值为-1。`t` 相对本轮记录起点，清点起止为引擎实时秒；文件头的 `engineTimeAtStart` 可将两者对齐。每条记录保存当时的帧率限制、垂直同步、窗口焦点、时间缩放、物理间隔、诊断阈值、清点状态及其成本。阶段的ValidReads表示成功读取次数，不声称是不同原生帧数。计时源在停止或换场景时可能释放，文件头只报告导出时状态；每条记录的-1才决定该时段是否有计时数据。

手动导出会将 `EVENT` 与性能记录按时间合并；即使较旧的清点结果较晚才被发现，也按其清点结束时间排列。事件含before/after、baselineT、lastT、peak、repeats及当时阈值，不用导出时的配置覆盖历史。默认不持续写盘，也不为每个突变输出BepInEx日志；事件写入内存，统一手动导出。

离线验证：`dotnet run --project tools/PerfTrackerTests/PerfTrackerTests.csproj -c Release`，覆盖环形覆盖／扩缩容、非等间隔时间查询、0.83与3.72的调度反例、历史设置和成本快照、未知值区别于零。

带 `-cumodtest` 或 `cumod.selftest` 启动时，在菜单用临时对象检查清醒／休眠、停用与父级过滤、碰撞分类、零预算让步、重叠场景根去重；同一帧销毁，不运行测试物品的Start/Update，不改真实物品。随后验证实际场景分帧清点，并输出 `[PERFTEST]`。启动和界面自检不能代替真实三人联机的前后对比，也不用于宣称FPS提升比例。

本机验证（2026-11-21）：Release构建零警告／零错误；离线164,808项断言通过，新增异常基线、最小增量、冷却合并、时间排序、缺失GPU、失焦、预热与文本标记检查；游戏内临时对象分类、实际菜单场景清点及界面轮播通过。逐项计时试读得到主线程约1.8ms、主动限帧等待约14.8ms；后台菜单的GPU/渲染计时与准确2D模拟计时未取得有效数据。尚未实测三人联机掉线前后或可见世界中的GPU计时，不能宣称已定位具体卡顿根因。
